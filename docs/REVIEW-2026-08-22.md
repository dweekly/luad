# `luad` review — 2026-08-22

Scope: PRD.md (Draft 1), the current implementation (6 commits, `cc359ef`), and
COMPOSABLE_RESEARCH_WORKFLOWS_PROPOSAL.md.

Verdict: the PRD is unusually good and the implementation currently fails its
most important claims. The gap is not a matter of unfinished phases — the
proof apparatus that was supposed to prevent exactly this failure was built in
a form that cannot detect it.

---

## 1. Confirmed implementation defects

All four were found by comparing `luad` output against `luac -l -l` by hand.
All four are in code paths whose phase is marked "complete" in the commit log.

### 1.1 Lua 5.4 `iABC` bitfield positions are wrong (critical)

`crates/luad-dialect-lua54/src/opcodes.rs:346-352`

```rust
let b = ((word >> 15) & 0xFF) as u8;   // must be >> 16
let c = ((word >> 23) & 0xFF) as u8;   // must be >> 24
let k = ((word >> 31) & 0x1) as u8;    // must be >> 15
```

Lua 5.4 packs `OP:0..6, A:7..14, k:15, B:16..23, C:24..31`. The current code
reads `B` starting at the `k` bit, so every decoded `B` is `(realB << 1) | k`
and every `C` is `(realC << 1) | (realB >> 7)`.

Empirical proof, `tests/fixtures/control_flow.lua` compiled with
`lua@5.4/bin/luac`:

| PC | word | `luac -l -l` | `luad disasm` |
|---:|---|---|---|
| 14 | `0x050100a2` | `ADD 1 1 5` | `ADD 1 2 10` |
| 29 | `0x00010180` | `MOVE 3 1` | `MOVE 3 2 0` |
| 30 | `0x01030146` | `RETURN 2 3 1` | `RETURN 2 6 2` |

`Bx`, `Ax` and `sJ` are extracted correctly, which is why control flow looks
plausible while every register operand is wrong.

Note that `crates/luad-dialect-lua55/src/opcodes.rs:326-336` gets the identical
layout right. The two dialects were evidently written independently with no
cross-check, and nothing in the test suite compares them.

### 1.2 `sB`/`sC` bias is never applied (5.4 and 5.5)

Lua 5.4/5.5 signed operands `sB`/`sC` are biased by `OFFSET_sB = 127`. No such
constant exists anywhere in the tree.

Against `luac` 5.5.1:

| `luac` | `luad` |
|---|---|
| `GTI 0 5 0` | `GTI 0 132 0` |
| `ADDI 0 0 1` | `ADDI 0 0 128` |
| `ADDI 0 0 -1` | `ADDI 0 0 126` |
| `EQI 1 15 0` | `EQI 1 142 0` |

This violates FR-DIS-004 ("Preserve both encoded and interpreted signed
values") — only the encoded value is present, and it is presented as if it
were the interpreted one.

### 1.3 Lua 5.4 opcode mode table misclassifies five opcodes

`crates/luad-dialect-lua54/src/opcodes.rs` marks `EQI`, `LTI`, `LEI`, `GTI`,
`GEI` as `IAsBx`. They are `iABC` (`A sB k`). This is what produces the
`GTI 0 -65271` garbage in the 5.4 listing — an `sBx` read of an `iABC` word.

### 1.4 Immediate-dominator computation always returns the entry block

`crates/luad-analysis/src/cfg.rs:391-401`

```rust
let is_closest = strict_doms
    .iter()
    .all(|&other| other == candidate || !candidate_doms.contains(&other));
```

`idom(n)` is the strict dominator of `n` that *is dominated by* every other
strict dominator of `n`. The predicate here selects the strict dominator that
is dominated by *no* other — which is always block 0. Combined with `break` on
first match over an ascending `BTreeSet`, every reachable block reports
`idom = b0`.

Observable: `luad cfg` on `control_flow.lua` reports `idom=b0` for all 15
non-entry blocks, including a block whose sole non-loop predecessor is `b4`.

### 1.5 Second-order effect

`luad validate` on the 5.4 fixture emits two `L54-VAL-REG-001` warnings
(`Register R(248) exceeds maxstacksize 6`) — the validator observed the
consequences of 1.1 — and still returns verdict `ValidForAnalysis` with exit 0.
Per FR-VAL-003 and §8.2 ("Analyzers … declare their preconditions"), an
out-of-bounds register reference is not a warning and the chunk is not
valid-for-analysis.

## 2. Why the proof apparatus did not catch any of this

### 2.1 The differential oracle does not compare instructions

`crates/luad-oracle/src/listing_parser.rs` parses `mnemonic`, `operands_raw`,
and constant `raw_text` out of the `luac -l -l` dump — and
`assert_chunk_matches_luac` never reads any of them. What it actually asserts:

- prototype count, `linedefined`, `lastlinedefined`, `numparams`, `is_vararg`,
  `maxstacksize`
- instruction **count** and per-PC **line numbers**
- constant **count** (never a value)
- local count + names, upvalue count + names

PRD §10.2 step 5 requires comparison of "opcode identity, operands, constants."
None of the three is compared. The tool named
`test_canonical_differential_oracle_lua54` would pass with a completely
scrambled opcode table.

### 2.2 The oracle skips silently when a compiler is absent

`test_differential_oracle.rs` returns early with an `eprintln!` when the
compiler is not found. On this machine, 5.1/5.2/5.3 skip entirely — the test
reports `ok`. In CI the situation is worse:

- `.github/workflows/ci.yml` runs `./scripts/install_ci_compilers.sh || true`
- `scripts/install_ci_compilers.sh` builds 5.1/5.2/5.3/5.4 only — **no 5.5**
- inside it, `make all -j4 || make generic -j4 || true` swallows build failure
- tarballs are fetched with no checksum, contradicting §10.1's requirement to
  record the exact upstream archive hash
- the script builds 5.4.**7**; `capabilities` claims oracle testing against
  5.4.**8**

Net: CI can be fully green with zero differential verification of any dialect.

### 2.3 "100% byte accounting" is a tautology

`verify_byte_accounting` asserts `header.byte_length == 31` and
`31 + 1 + main_proto.byte_length == input.len()`, where `byte_length` is
derived from cursor positions. It cannot fail for any input that parses. §10.4
asks for every byte to be classified as recognized field / padding /
preserved-uninterpreted / diagnosed-trailing. That is not implemented.

### 2.4 The evidence manifest is hand-written prose

`crates/luad-core/src/capabilities.rs:154` hard-codes the strings printed by
`luad capabilities --evidence`, including:

> "Field-by-field canonical differential testing against official Lua 5.1.5,
> 5.2.4, 5.3.6, 5.4.8, 5.5.1 compiler dumps"

false on both counts. Every dialect's structured `evidence` array is `[]`.
`README.md` says 5.1–5.3 are "In progress" while `capabilities` reports them
`supported` — two claim sources already disagreeing on day two.

This is precisely the deficiency PRD §1.4 item 8 identifies in the existing
ecosystem. The implementation currently reproduces the problem it was written
to solve.

## 3. Course correction

### 3.1 Stop-the-line items, in order

1. **Add a negative control for the oracle.** For each dialect, a test that
   perturbs one opcode name, one bitfield position, and one constant tag, and
   asserts the differential comparison *fails*. Without this an oracle that
   compares nothing is indistinguishable from one that compares everything.
   This is the single highest-value missing test in the project.

2. **Add the instruction-word round trip.** `encode(decode(word)) == word`, as
   a property test over all `u32` (or a large sample) per dialect, with the
   encoder written independently from the decoder's field table. This needs no
   oracle, no compiler, and catches defect 1.1 immediately — `(B << 1) | k`
   cannot re-encode.

3. **Make the oracle compare mnemonics, operands, and constant values.** Fix
   `assert_chunk_matches_luac` to assert on the fields it already parses. Then
   fix 1.1–1.3 until it passes.

4. **Make missing compilers a hard failure.** Delete the skip branches; delete
   `|| true` from CI; pin and checksum the Lua tarballs; build 5.5. A skipped
   proof gate must be a red build, not a silent pass.

5. **Fix the dominator predicate** (1.4) and add hand-authored expected
   dominator trees for the branching fixtures, as Phase 3's exit gate already
   requires.

6. **Derive `capabilities` from evidence, not from a `vec![]`.** Emit gate
   results to a generated file at build/test time; have `capabilities` read it;
   a dialect with no passing gate reports `experimental`, never `supported`.
   Make `README.md` generated from the same source.

### 3.2 Process change

The PRD's §15 risk row "Supporting all versions at once creates shallow
coverage → deliver one vertical slice and advertise versions only after
independent gates pass" describes exactly what happened, despite being written
down. Prose gates in a 1163-line document do not gate anything.

Convert each phase exit gate into a named CI job (`gate-phase1-lua54`,
`gate-phase2-lua54`, …). A phase is complete when its job is green in CI, not
when a commit message says so. Six commits closing nine phases is a signal, not
an achievement.

### 3.3 The un-oracled layer, and what to do about it

`luac -l -l` cannot validate the most valuable thing `luad` claims: instruction
*effects* — register reads/writes, ranges, multireturn, metamethod fallbacks
(FR-DIS-008/009/011, FR-AN-005). §15's mitigation for this is "`lvm.c` review,"
i.e. unautomatable human judgment. That is the project's real long pole and it
deserves its own phase and its own mechanism.

Concrete proposal: a **test-only instrumented VM oracle**. Patch `lvm.c` (a few
hundred lines) to log, per executed instruction, the actual set of stack slots
read and written; run the fixture corpus; diff against `luad`'s declared
effects. This converts the semantic layer from "reviewed" to "tested" and is
the only route to honest FR-DIS-008 evidence. It is the highest-leverage
addition to the PRD.

### 3.4 PRD-level suggestions

- **Pull the serializer forward from Phase 9 to Phase 1.** `parse → serialize →
  byte-identical` is the cheapest real losslessness proof and replaces §2.3's
  tautological byte accounting. It needs no assembly *language*, just a writer.
- **Narrow v1 to Lua 5.4 + 5.5.** Five dialects at v1 multiplies proof cost
  without proportionate user value; 5.2 in particular is rare in the wild. Ship
  5.4/5.5 with real evidence, then 5.1 (which needs the *most* care, being the
  version most often confused with LuaJIT), then 5.3, then 5.2.
- **Require patch-range evidence.** "Lua 5.4.0 – 5.4.8" as a single dialect is
  an untested assertion. Require the fixture corpus to be compiled with every
  patch release in a claimed range and to parse identically, or narrow the
  claim.
- **Answer the positioning question explicitly.** The PRD hedges on whether
  `luad` is a correctness artifact or a tool people use. If the latter, LuaJIT
  and Luau — where most real-world Lua bytecode actually lives (games, Roblox,
  embedded/OpenResty) — matter more than Lua 5.2, and Phase 8 should move up.
  If the former, the current ordering is right. Pick one and say so in §2.1.
- **Replace `unsafe { transmute }` in all five opcode tables** with a generated
  `match`, and add `#![forbid(unsafe_code)]`. It is sound today, but the README
  sells "zero unsafe memory loads," and a future variant with a discriminant
  gap turns it into UB silently.
- Missing repo hygiene per house convention: no `ROADMAP.md`, no
  `CHANGELOG.md`.

## 4. Composable research workflows proposal

The boundary this proposal draws — `luad` owns deterministic facts, the caller
owns accumulated interpretation — is correct, well argued, and worth keeping.
The "complexity budget" section is the strongest piece of writing in either
document. Statelessness, hash-scoped identity, and presentation-only overlays
are all right.

Reservations:

1. **It is premature.** Every milestone presupposes a trustworthy fact layer.
   Today `get` would return wrong operands, `slice` would traverse a broken
   dominator tree, and an overlay would bind labels to misdecoded instructions.
   Freeze it until §3.1 is done. Nothing in the proposal is invalidated by
   waiting; a schema shipped over wrong facts is much harder to walk back.

2. **`get`, `explain`, and `query` overlap.** The proposal concedes `get` and
   `explain` "share resolver code." Go further: make `get` the primitive and
   re-express `explain` as a text renderer over `get --include semantic`. A
   fourth retrieval command is how §15's "CLI becomes a collection of
   inconsistent commands" risk materializes.

3. **`ArtifactRef` under-specifies its own scope.** The proposal states
   correctly that IDs are stable within "one exact chunk" — but §7.1 of the PRD
   says "within a specific input **and selected parse interpretation**." Parse
   mode, dialect override, and (later) vendor profile all change the prototype
   tree. A ref carrying only `artifact_sha256` will silently mis-bind an
   overlay authored under permissive parse when replayed under strict. Include
   the resolved dialect/profile hash and parse mode in the ref.

4. **Rename `slice`.** PRD FR-AN-010 reserves "backward slicing" for real
   dataflow slicing. Shipping `luad slice` meaning "bounded graph neighborhood"
   guarantees confusion when the real thing arrives. `neighborhood`, `expand`,
   or `graph` are all free.

5. **Swap `slice` for `export` in the first pass.** The proposal's own workflow
   example shows a caller stitching N invocations to build its own index. If
   the caller owns the database, the primitive it actually wants is one
   deterministic full-fidelity dump — `luad export --format jsonl` — not a
   traversal engine inside `luad`. It is cheaper to specify, far cheaper to
   prove correct, and more faithful to the stated boundary. Rank it above
   `slice`.

6. **Overlay hardening.** `attributes: BTreeMap<String, JsonValue>` is
   caller-supplied data that reaches a terminal and DOT output. State
   explicitly that overlay strings pass through the same control-character and
   bidi escaping as chunk strings (§9.2) — shared overlays are an untrusted
   input path. Also make the unresolved-target policy an explicit flag
   (`--overlay-unresolved=error|warn|ignore`, default `error`) rather than
   "an error by default."

7. **Add one line to the complexity budget:** no new command may expose a fact
   that is not covered by a passing oracle gate.

Recommended order once the fact layer is trustworthy: `get` → overlays →
`export` → (defer neighborhood traversal until someone has a concrete workflow
that `export` cannot serve).
